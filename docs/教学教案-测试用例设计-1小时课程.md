# 测试用例设计方法课程教案 —— 60分钟课堂教学设计

**课程主题**：测试用例设计方法与实践
**授课对象**：QA工程师 / 测试新人
**课程时长**：60分钟
**教学案例**：票多星(TicketMore)票务平台
**教学方法**：理论讲解 + 案例演示 + 随堂练习 + 互动讨论

---

## 一、课程目标

| 维度 | 目标 |
|------|------|
| 知识 | 掌握等价类划分、边界值分析、判定表、状态转换、场景法五大用例设计方法 |
| 技能 | 能从需求文档中提取测试点，用正确的方法设计出规范、可执行的测试用例 |
| 思维 | 建立"用方法而非直觉"设计用例的专业思维，理解每种方法的适用场景 |

*（让2-3个学生回答，可能的回答：用户名不填、密码不填、手机号不填、全部正确填写……大约会说出4-5种情况）*

### 【环节二】方法一：等价类划分法（10分钟）

**（0:05 - 0:07）概念讲解（2 min）**

> **等价类划分法的核心思想**：把输入数据分成若干等价类，每个等价类中的数据对程序的测试效果是等价的。从每个等价类中选一个代表值测试即可。

**为什么需要它？**
- 穷举测试不可能（手机号有10^11种组合）
- 用最少的用例覆盖最多的场景

**等价类的两种类型：**

| 类型 | 定义 | 示例（手机号） |
|------|------|---------------|
| 有效等价类 | 符合需求、能正常处理的输入 | 13812345678 |
| 无效等价类 | 不符合需求、应被拒绝的输入 | 空、1381234567(10位)、138123456789(12位)、abc |

**（0:07 - 0:10）案例演示：票多星用户注册（3 min）**

> 我们以票多星用户注册为例：`POST /api/user/register`，三个必填字段：username、password、phone。

**第一步：分析每个字段的等价类**

```
【username 字段】
  有效等价类：
    E1: 合法用户名（4-20位字母数字下划线），如 "test_user_001"
  无效等价类：
    E2: 空字符串
    E3: 太短（<4位），如 "abc"
    E4: 太长（>20位），如 "a"×21
    E5: 含特殊字符，如 "test@user"
    E6: 已存在的用户名

【password 字段】
  有效等价类：
    E7: 合法密码（6-20位任意字符），如 "Pass123456"
  无效等价类：
    E8: 空字符串
    E9: 太短（<6位），如 "12345"
    E10: 太长（>20位），如 "a"×21

【phone 字段】
  有效等价类：
    E11: 合法手机号（1[3-9]xxxxxxxxx），如 "13812345678"
  无效等价类：
    E12: 空字符串
    E13: 格式不符（不以1开头），如 "23812345678"
    E14: 格式不符（第二位不在3-9），如 "12812345678"
    E15: 长度不对（10位/12位），如 "1381234567"
    E16: 含非数字字符，如 "1381234567a"
    E17: 已注册的手机号
```

**第二步：设计用例覆盖这些等价类**

> 原则：一条用例可以覆盖多个有效等价类，但每条用例只能覆盖一个无效等价类。

| 用例ID | 覆盖等价类 | username | password | phone | 预期结果 |
|--------|-----------|----------|----------|-------|---------|
| TC-REG-001 | E1,E7,E11 | test_user_001 | Pass123456 | 13812345678 | code=0 注册成功 |
| TC-REG-002 | E2 | (空) | Pass123456 | 13812345678 | 100601 参数缺失 |
| TC-REG-003 | E3 | abc | Pass123456 | 13812345678 | 100602 参数无效 |
| TC-REG-004 | E6 | (已存在) | Pass123456 | 13812345678 | 100106 用户名已存在 |
| TC-REG-005 | E8 | test_user_002 | (空) | 13812345679 | 100601 参数缺失 |
| TC-REG-006 | E9 | test_user_003 | 12345 | 13812345680 | 100602 参数无效 |
| TC-REG-007 | E12 | test_user_004 | Pass123456 | (空) | 100601 参数缺失 |
| TC-REG-008 | E15 | test_user_005 | Pass123456 | 1381234567 | 100602 参数无效 |

> **一个关键原则**：有效等价类可以组合（一条用例测多个有效输入），无效等价类要独立（一次只测一个无效输入，否则你不知道是哪个触发的错误）。

**（0:10 - 0:12）等价类划分的适用场景总结（2 min）**

| 适用场景 | 示例 |
|----------|------|
| 输入有明确取值范围 | 手机号格式、金额范围 |
| 输入有明显的分类 | 支付渠道(alipay/wechat/bank/unionpay) |
| 输出有明显分类 | 订单状态(1-6) |

> "等价类划分让你用8条用例覆盖了原来可能写30条才能覆盖的范围 —— **不是偷懒，是聪明**。"

**（0:12 - 0:15）课堂小练习（3 min）**

> 用等价类划分法分析票多星**优惠券领取**功能：
> - couponId：必填，1-99999999的整数
> - 每人限领数量：同一优惠券不超过3张
> - 库存：remainCount > 0
>
> 请写出至少6条用例，覆盖有效和无效等价类。

*（让学生思考2分钟，然后公布参考答案）*

**参考答案：**
```
有效等价类：合法couponId + 未达限领 + 有库存 → 领取成功
无效等价类：
  1. couponId为空 → 参数缺失
  2. couponId为0 → 参数无效
  3. couponId为负数 → 参数无效
  4. couponId不存在 → 优惠券不存在
  5. 已达限领3张 → 限领达上限
  6. 库存为0 → 优惠券已领完
```

### 【环节三】方法二：边界值分析法（10分钟）

**（0:15 - 0:17）概念讲解（2 min）**

> 业界有一个著名的统计数据：**软件缺陷中约70%集中在输入域的边界上**。边界值分析是公认找bug最高效的方法。

> **核心思想**：等价类划分告诉你测"代表值"，边界值分析告诉你测"拐点"。

**边界值分析的三点法：**

```
对于边界值 N：
  测 N-1（边界下方）
  测 N（边界本身）
  测 N+1（边界上方）

示例：密码长度要求6-20位
  测 5位（min-1）   ← 应拒绝
  测 6位（min）     ← 应接受
  测 7位（min+1）   ← 应接受
  测 19位（max-1）  ← 应接受
  测 20位（max）    ← 应接受
  测 21位（max+1）  ← 应拒绝
```

**（0:17 - 0:21）案例演示：票多星订单创建（4 min）**

> 票多星订单创建有多个边界值，我挑3个典型的来演示。

**边界1：每人每单限购10张**

```
测试用例：
  TC-BV-001: quantity=9   → 创建成功（边界下方）
  TC-BV-002: quantity=10  → 创建成功（边界本身）
  TC-BV-003: quantity=11  → 返回100310（边界上方，超限）
```

**边界2：退款费率按时间分界（这是绝佳边界场景）**

```
规则：
  演出前 >=7天：退100%
  演出前 3-7天：退70%（注意：3天不含，7天含）
  演出前 1-3天：退50%
  演出前 <1天：退0%

边界值设计：
  演出前 7天0时0分   → 退100%（边界，刚满7天）
  演出前 6天23时59分  → 退70%（边界下方，不满7天）
  演出前 3天0时0分   → 退70%（边界，刚满3天）
  演出前 2天23时59分  → 退50%（边界下方，不满3天）
  演出前 1天0时0分   → 退50%（边界，刚满1天）
  演出前 0天23时59分  → 退0%（边界下方，不满1天）
  演出后 1天         → 退0%（不可退）
```

> 这个例子请特别注意：**边界值分析的难点不是方法本身，而是准确理解业务规则的边界定义**。"3-7天"到底是含不含3天？含不含7天？这是你设计用例之前必须搞清楚的问题。

**边界3：支付超时时间（15分钟）**

```
  TC-BV-007: 14分59秒时发起支付 → 应成功
  TC-BV-008: 15分00秒时发起支付 → 应失败(订单已过期)
  TC-BV-009: 15分01秒时发起支付 → 应失败(订单已过期)
```

**（0:21 - 0:25）课堂练习（4 min）**

> 票多星用户修改密码功能，新密码要求6-20位。另外，用户评论评分范围1-5星。请用边界值分析法各设计3条用例。

*（学生练习2分钟，然后公布答案）*

```
密码边界值：
  5位 → 拒绝(min-1)
  6位 → 接受(min)
  20位 → 接受(max)
  21位 → 拒绝(max+1)

评分边界值：
  0星 → 拒绝(min-1)
  1星 → 接受(min)
  5星 → 接受(max)
  6星 → 拒绝(max+1)
```

### 【环节四】方法三：判定表法（10分钟）

**（0:25 - 0:28）概念讲解（3 min）**

> 前面两种方法处理"单个输入"的测试。但实际业务中，很多输出依赖于**多个条件的组合**。这时候用判定表法。

> **判定表法的核心**：列出所有条件及其取值组合 → 确定每种组合对应的动作 → 化简合并 → 一条规则一条用例。

**判定表结构：**

```
┌──────────────────────────────────────┐
│            条件桩（条件列表）          │
├──────────────────────────────────────┤
│            条件项（条件取值组合）       │
├──────────────────────────────────────┤
│            动作桩（动作列表）          │
├──────────────────────────────────────┤
│            动作项（每种组合的结果）     │
└──────────────────────────────────────┘
```

**（0:28 - 0:33）案例演示：票多星退款判断（5 min）**

> 我们用判定表来分析票多星的退款资格判断，这涉及3个条件。

**条件：**
- C1: 订单是否已支付？（是/否）
- C2: 是否已申请过退款？（是/否）
- C3: 距演出开始时间？（>=7天 / 3-7天 / 1-3天 / <1天 / 已开始）

**动作：**
- A1: 允许退款，退100%
- A2: 允许退款，退70%
- A3: 允许退款，退50%
- A4: 拒绝退款（原因：不可退时段）
- A5: 拒绝退款（原因：未支付）
- A6: 拒绝退款（原因：已申请过）

**判定表（化简前共10条规则）：**

| 规则编号 | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 |
|----------|----|----|----|----|----|----|----|----|
| C1:已支付 | Y | Y | Y | Y | Y | N | Y | Y |
| C2:已申请过 | N | N | N | N | Y | - | N | N |
| C3:距演出 |>=7天|3-7天|1-3天|<1天| - | - |已开始|已结束|
| A1:退100% | ✓ |   |   |   |   |   |   |   |
| A2:退70%  |   | ✓ |   |   |   |   |   |   |
| A3:退50%  |   |   | ✓ |   |   |   |   |   |
| A4:拒绝-时段|   |   |   | ✓ |   |   | ✓ | ✓ |
| A5:拒绝-未付|   |   |   |   |   | ✓ |   |   |
| A6:拒绝-重复|   |   |   |   | ✓ |   |   |   |

**化简后对应测试用例：**

| 用例ID | 场景 | 预期 |
|--------|------|------|
| TC-REF-001 | 已支付+未申请+距演出>=7天 | code=0, 退100% |
| TC-REF-002 | 已支付+未申请+距演出3-7天 | code=0, 退70% |
| TC-REF-003 | 已支付+未申请+距演出1-3天 | code=0, 退50% |
| TC-REF-004 | 已支付+未申请+距演出<1天 | code=100504, 不可退 |
| TC-REF-005 | 已支付+已申请过退款 | code=100501, 已处理 |
| TC-REF-006 | 未支付的订单申请退款 | code=100504, 不可退 |
| TC-REF-007 | 已支付+未申请+演出已开始 | code=100504, 不可退 |

**（0:33 - 0:35）适用场景总结（2 min）**

> 判定表法最适合的场景：**if-else特别多的业务逻辑**。
> - 退款规则
> - 优惠券使用条件判断
> - 权限判断
> - 费用计算

> **记住**：当你在需求文档里看到超过2个"如果……则……"，就要想到用判定表。

### 【环节五】方法四：状态转换法（8分钟）

**（0:35 - 0:37）概念讲解（2 min）**

> 很多系统都有"状态"的概念。订单有待支付、已支付、已完成；优惠券有未使用、已使用、已过期。**状态转换法专门测试状态流转逻辑**。

> **核心任务**：
> 1. 画出状态图（列出所有状态和合法转换路径）
> 2. 设计用例覆盖每条合法路径
> 3. 设计用例验证非法路径被正确拦截

**（0:37 - 0:41）案例演示：票多星订单状态机（4 min）**

> 票多星订单有6种状态，我们先画出状态转换图。

**订单状态转换图：**

```
           创建订单
              ↓
      ┌──────────────┐
      │ 1.PENDING_PAY│──── 超时/用户取消 ──→ 4.CANCELLED
      │   待支付      │
      └──────┬───────┘
             │ 支付成功
             ↓
      ┌──────────────┐
      │   2.PAID     │──── 申请退款 ──→ 6.REFUNDING ──→ 5.REFUNDED
      │    已支付     │
      └──────┬───────┘
             │ 确认完成
             ↓
      ┌──────────────┐
      │ 3.COMPLETED  │
      │    已完成     │
      └──────────────┘
```

**设计测试用例 —— 合法路径覆盖（最少5条）：**

| 用例ID | 状态转换路径 | 触发操作 |
|--------|-------------|---------|
| TC-FSM-001 | 1→2（待支付→已支付） | 完成支付 |
| TC-FSM-002 | 1→4（待支付→已取消） | 取消订单 |
| TC-FSM-003 | 2→3（已支付→已完成） | 确认完成 |
| TC-FSM-004 | 2→6→5（已支付→退款中→已退款） | 申请退款+退款成功 |

**设计测试用例 —— 非法路径（至少3条）：**

| 用例ID | 非法转换 | 预期 |
|--------|---------|------|
| TC-FSM-005 | 4→2（已取消→已支付） | 拒绝，状态错误 |
| TC-FSM-006 | 3→6（已完成→退款中） | 拒绝，不可退款 |
| TC-FSM-007 | 1→3（跳过支付直接完成） | 拒绝，状态错误 |

**状态转换法的"全覆盖准则"：**
- 每个状态至少被访问一次
- 每条合法的转换至少被遍历一次
- 每条非法的转换至少被验证一次（系统能正确拦截）

**（0:41 - 0:43）适用场景（2 min）**

> 一句话判断要不要用状态转换法：**被测对象是否有明确的状态流转？** 有，就用。
> - 订单、支付、退款
> - 优惠券（未使用→已使用/已过期）
> - 用户（正常→禁用→待审核）
> - 票品（待售→在售→售罄→下架→结束）

### 【环节六】方法五：场景法（5分钟）

**（0:43 - 0:46）概念讲解 + 案例（3 min）**

> 前四种方法都是从"输入/逻辑/状态"角度分析。但最终用户不会按你的等价类来用系统。**场景法从用户的真实使用路径出发，模拟端到端的业务流程。**

**场景法 = Happy Path（主流程）+ Alternative Path（备选流程）+ Error Path（异常流程）**

> 票多星的"购票支付"主场景：

```
1. 浏览票品列表 → 2. 查看演出详情 → 3. 选择场次/票档
→ 4. 加入购物车 → 5. 进入结算 → 6. 选择优惠券
→ 7. 创建订单 → 8. 选择支付方式 → 9. 完成支付 → 10. 查看订单
```

**场景覆盖矩阵：**

| 场景类型 | 描述 | 用例 |
|----------|------|------|
| 基本流（Happy Path） | 全部步骤成功 | TC-SCENE-001: 全流程走通 |
| 备选流1 | 不使用优惠券 | TC-SCENE-002: 第6步跳过 |
| 备选流2 | 从票品详情直接购买（跳过购物车） | TC-SCENE-003: 第4步跳过 |
| 异常流1 | 支付时余额不足 | TC-SCENE-004: 第8步失败 |
| 异常流2 | 支付超时 | TC-SCENE-005: 第8步超时 |
| 异常流3 | 支付时库存被抢光 | TC-SCENE-006: 第8步失败 |

**（0:46 - 0:48）场景法的设计技巧（2 min）**

> - **先画流程图，再写用例**：流程图比文字更直观，不容易漏分支
> - **先通基本流，再补备选和异常**：基本流不通，其他都没意义
> - **场景法适合做冒烟测试和回归测试**：3-5条核心场景用例，每次发版前跑一遍

### 【环节七】用例编写规范与综合实践（8分钟）

**（0:48 - 0:52）用例编写规范（4 min）**

> 不管你用什么方法设计，最终写出来的用例格式应该统一。我们看票多星项目使用的标准用例模板。

**标准用例模板与字段说明：**

```
┌─────────────────────────────────────────────────────────────┐
│ 用例编号    [模块缩写]-[功能缩写]-[序号]                       │
│            例: TC-PAY-CREATE-001                             │
│            模块: USER/TICKET/ORDER/CART/COUPON/PAY/ADMIN      │
├─────────────────────────────────────────────────────────────┤
│ 用例标题    简洁描述测试目的，格式: [条件]下[操作]，[预期结果]   │
│            例: "余额充足的用户使用微信支付，支付成功"             │
├─────────────────────────────────────────────────────────────┤
│ 优先级      P0:核心功能/涉及资金/阻塞其他测试                   │
│             P1:重要功能/高频使用                               │
│             P2:一般功能/低频使用                               │
│             P3:建议优化/体验类                                 │
├─────────────────────────────────────────────────────────────┤
│ 前置条件    执行用例前必须满足的条件                            │
│             (数据准备、环境配置、依赖状态)                       │
├─────────────────────────────────────────────────────────────┤
│ 测试数据    用例用到的具体数据                                 │
├─────────────────────────────────────────────────────────────┤
│ 测试步骤    编号的、可执行的操作步骤                            │
│             一个等号（=）一个步骤                               │
├─────────────────────────────────────────────────────────────┤
│ 预期结果    每个步骤对应的预期输出                              │
│             必须具体、可量化                                   │
│             "返回成功" ❌                                      │
│             "返回 code=0, data.orderStatus=1" ✅              │
├─────────────────────────────────────────────────────────────┤
│ 清理步骤    测试完成后的数据清理                                │
│             (删除测试数据、恢复状态)                            │
├─────────────────────────────────────────────────────────────┤
│ 设计方法    本条用例使用的设计方法                              │
│             (等价类/边界值/判定表/状态转换/场景法)               │
├─────────────────────────────────────────────────────────────┤
│ 关联需求    对应的需求编号 (FR-ORDER-001)                      │
└─────────────────────────────────────────────────────────────┘
```

**用例编写原则（黄金三法则）：**
1. **一条用例只测一个核心验证点**—— 不要把5个场景塞进1条用例
2. **预期结果必须可量化**—— 不能写"系统正常"，要写具体返回的code和数据
3. **步骤要能让另一个测试人员照着执行**—— 写步骤时想象你请假了，同事能否看懂

**（0:52 - 0:56）综合实践（4 min）**

> 现在我们综合运用今天学的方法，为票多星"创建支付"功能设计用例。

**需求回顾：**
```
POST /api/payment/create
参数: orderNo(必填), amount(必填), payChannel(必填: alipay/wechat/bank/unionpay)
规则: 订单必须PENDING_PAY状态，金额必须=订单payAmount
```

**综合用例设计（现场演示5条）：**

| 用例ID | 方法 | 场景 | 预期 |
|--------|------|------|------|
| TC-PAY-001 | 场景法(基本流) | 待支付订单+金额匹配+微信支付 → 创建成功 | code=0 |
| TC-PAY-002 | 等价类(无效) | orderNo为空 | code=100601 |
| TC-PAY-003 | 等价类(无效) | payChannel为不支持的值"bitcoin" | code=100404 |
| TC-PAY-004 | 边界值 | amount=0.01(最小合法金额) | code=0 |
| TC-PAY-005 | 状态转换(非法) | 用已取消的订单发起支付 | code=100304 |
| TC-PAY-006 | 判定表 | orderNo存在+金额匹配+有效渠道+PENDING_PAY状态 → 成功 | code=0 |

> 看到了吗？同一个功能，从不同方法切入，能发现完全不同的测试点。**方法不是让你多写用例，是让你不遗漏**。

### 【环节八】总结与常见误区（4分钟）

**（0:56 - 0:58）五种方法选择指南（2 min）**

| 你看到…… | 优先用…… |
|-----------|----------|
| 输入有取值范围/格式 | 等价类划分 + 边界值分析 |
| 多个条件决定不同结果 | 判定表法 |
| 对象有明确的状态流转 | 状态转换法 |
| 端到端的业务流程 | 场景法 |
| 以上所有情况 | **组合使用** |

> **组合使用的原则**：先用场景法覆盖主流程 → 用等价类+边界值分析输入 → 用判定表处理复杂逻辑 → 用状态转换验证状态流转。一个功能至少用2-3种方法交叉验证。

**（0:58 - 1:00）常见误区 + 课后作业（2 min）**

**6个初学者常见误区：**

| 误区 | 正确做法 |
|------|----------|
| "等价类划分就是把输入分成有效和无效两类" | 要先理解需求再划分，不是机械二分 |
| "边界值就是测最大最小值" | 还要测 min-1, max+1，以及内部边界（如7天/3天/1天） |
| "判定表画出来就行了" | 画完要化简，相同动作的相邻规则要合并 |
| "状态转换只测合法路径" | 非法路径的拦截验证同样重要 |
| "场景法就是写一条超长用例" | 基本流、备选流、异常流分开写成独立用例 |
| "用例写得越多越好" | 质量 > 数量。10条精准用例 > 50条冗余用例 |

**课后作业：**

> 使用今天学的5种方法，为票多星**订单模块**设计测试用例：
>
> 1. 等价类划分法：分析 CreateOrderRequest 的 contactPhone 字段，写出有效和无效等价类（至少4个）
> 2. 边界值分析法：分析每人每单限购10张的边界值（至少3条用例）
> 3. 判定表法：分析优惠券使用条件（已支付? + 在有效期内? + 满足最低消费?），画判定表并设计用例
> 4. 状态转换法：画出订单的6状态转换图，列出所有合法路径（至少4条用例）
> 5. 场景法：写出"选票→加购→下单→支付→查看订单"的基本流和至少2条异常流
>
> 要求：使用标准用例模板格式编写。
