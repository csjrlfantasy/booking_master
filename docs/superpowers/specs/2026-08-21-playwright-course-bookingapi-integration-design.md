# Playwright 课程与 BookingApi 实战联调设计

## 1. 目标

把 `D:\Education\playwright课程` 中同一门 Playwright Python 课程的三类代码呈现统一到真实的票务业务背景：

- 根目录企业级测试框架；
- `lessons` 下 32 课的示例、练习和参考答案；
- `图文课程` 下 36 单元配套代码及其交付压缩包。

真实被测系统统一为 `D:\AIProjects\BookingApi`。课程中的登录、搜索、用户、票品、订单、优惠券、API 与 UI 联动等业务示例直接操作 BookingApi；BookingApi 不具备的 iframe、拖拽等专项能力继续使用稳定的官方演示站。

## 2. 已确认约束

- 教师自行启动 BookingApi，本次改造不增加或接管启动脚本。
- UI 默认地址为 `http://127.0.0.1:3000`，API 默认地址为 `http://127.0.0.1:8088/api`。
- 地址和账号可通过环境变量覆盖，代码中不得散落硬编码环境值。
- 测试可以创建数据，但必须自动清理自己创建的数据。
- 不清空数据库，不修改或删除无法证明属于当前测试运行的数据。
- BookingApi 当前工作区已有用户修改，实施时只做与课程联调直接相关的增量编辑。
- 教学 README、练习、答案、运行命令和测试数据说明必须与代码同步。

## 3. 总体架构

BookingApi 是唯一真实业务系统。课程根目录提供一套规范化的 Playwright 测试框架，章节代码按教学进度逐步展示同一套能力，36 单元配套代码则提供适合图文课程分发的独立示例和最终项目快照。

四个边界明确的组件共同完成联调：

1. **BookingApi 可测试性契约**：稳定定位属性、开发环境测试数据清理入口，以及相应的后端和前端回归测试。
2. **课程公共测试底座**：环境配置、服务健康检查、唯一运行标识、认证 API 客户端、数据工厂和清理登记表。
3. **业务页面对象与测试**：管理端登录、商城搜索、用户管理，以及代表性的票品、订单和优惠券 API/UI 联动流程。
4. **章节内容映射**：把 32 课和 36 单元中适合票务项目的示例、练习、答案、配置和文档切换到 BookingApi；保留确有必要的专项演示站。

课程代码依赖公开的 UI/API 契约，不依赖 BookingApi 的 Java 内部实现。BookingApi 内部实现可以变化，只要 URL、响应契约和 `data-testid` 保持稳定，课程代码就无需跟随重写。

## 4. BookingApi 可测试性改造

### 4.1 稳定 UI 定位

在 React 管理端和商城的核心交互元素上补充语义明确的 `data-testid`，至少覆盖：

- 管理员登录表单、登录按钮和错误提示；
- 商城登录/注册切换、账号、密码和提交按钮；
- 商城票品搜索、分类筛选、票品卡片和空结果提示；
- 管理端导航、用户列表、新建用户、状态操作；
- 票品、订单和优惠券页面的关键表格、表单与操作反馈。

优先使用 Playwright 的角色、标签和可见文本定位；只有业务语义不足或文本会变化的关键控件才使用 `data-testid`。不为了测试改变页面行为或视觉样式。

### 4.2 测试数据清理

新增仅在 Spring `dev` profile 下启用的测试支持接口。接口要求 `X-Course-Test-Key` 请求头，密钥由 `COURSE_TEST_KEY` 环境变量覆盖，并提供仅适合本地教学环境的默认值。

清理请求携带本次运行的 `runId` 及测试记录下来的资源标识。后端在删除前再次验证资源的用户名、名称或备注包含 `pw-course-{runId}` 前缀；验证不通过时拒绝删除。清理按依赖顺序处理订单明细、支付/退款、用户优惠券、订单、身份信息、测试用户、测试票品和测试优惠券。

清理必须满足：

- 幂等：重复调用仍返回成功结果；
- 最小权限：非 dev 环境不注册接口，密钥不匹配返回拒绝；
- 最小范围：仅删除请求列出且带正确运行前缀的资源；
- 可追踪：返回各类已清理、未找到和拒绝清理的资源数量。

能通过现有公开业务 API安全清理的资源优先使用公开 API；测试支持接口只补足公开接口无法可靠清理的部分。

## 5. 课程公共测试底座

公共配置提供以下默认值和环境变量覆盖：

| 配置 | 默认值 | 环境变量 |
| --- | --- | --- |
| Web 根地址 | `http://127.0.0.1:3000` | `BOOKING_WEB_URL` |
| API 根地址 | `http://127.0.0.1:8088/api` | `BOOKING_API_URL` |
| 管理员账号 | `admin` | `BOOKING_ADMIN_USERNAME` |
| 管理员密码 | `Admin@123456` | `BOOKING_ADMIN_PASSWORD` |
| 清理密钥 | 本地教学默认值 | `COURSE_TEST_KEY` |

pytest 会话级预检查分别访问前端页面和后端健康接口。如果服务未启动，测试快速失败并输出明确地址和启动提示，不尝试启动项目。

每个创建数据的测试获得独立 `runId`，生成 `pw-course-{runId}-...` 格式的用户名、昵称、票品名、优惠券名和备注。数据登记表记录创建成功后返回的资源 ID；`yield` fixture 的终结阶段即使测试断言失败也会执行清理。清理失败作为独立错误报告，不覆盖原始测试失败原因。

## 6. 根目录企业级示例

根目录页面对象和测试改为真实业务实现：

- `LoginPage` 操作管理端 `/login`，覆盖成功、错误密码、空值校验和登录态断言；
- `SearchPage` 操作商城 `/shop`，覆盖关键词、分类、无结果和详情跳转；
- `UserManagementPage` 操作管理端 `/users`，覆盖列表、创建、详情、角色或状态变更；
- API 客户端负责管理员/用户认证、数据准备、业务断言和清理登记；
- 测试数据从占位姓名和 URL 改为带运行前缀的票务领域数据。

断言不止检查页面可见或 HTTP 200，还验证业务响应 `code`、关键字段、UI 结果、状态变化和必要的后端副作用。

## 8. 数据流

典型 API/UI 联动测试的数据流如下：

1. 健康检查确认前端和后端可用。
2. fixture 生成唯一 `runId`，通过 API 登录管理员或创建临时用户。
3. API 创建或查询测试所需业务数据，并把资源 ID 登记到清理表。
4. Playwright 打开真实页面，以 UI 完成被测操作。
5. UI 断言验证用户可见结果，API 查询验证后端状态或副作用。
6. fixture 在测试结束时提交清理表，BookingApi 校验前缀后删除本次运行数据。

只读测试不创建数据，也不调用清理接口。并行测试通过不同 `runId` 隔离，禁止依赖固定用户或固定订单状态。

## 9. 错误处理

- 前端或后端不可用：预检查立即失败，给出不可访问的具体 URL。
- 登录失败：错误中标明账号来源，但不打印密码或 token。
- 测试数据准备失败：停止业务步骤，并清理此前已登记的数据。
- UI 元素契约变化：定位器失败应指向具体页面对象和 `data-testid`，保留截图与 trace。
- 清理验证失败：保留数据并报告拒绝原因，绝不放宽前缀保护。
- 外部专项演示站不可用：相关测试使用独立标记，可与核心 BookingApi 测试分开运行。

- 后端单元/控制器测试验证 dev 限制、密钥校验、前缀保护、依赖顺序和幂等清理。

- Maven 与前端测试只运行受本次改动影响的目标集，再执行完整可行回归。

- 对所有 Python 文件执行语法编译检查。
- 执行 `pytest --collect-only`，保证章节示例和根目录测试可收集。

- 核心冒烟结束后查询确认本次 `runId` 数据已清理。
- 检查 32 课、36 单元 README/代码中的占位业务 URL；允许保留的外部地址必须属于专项功能白名单。
- 重新生成并核验图文课程交付压缩包和 `MANIFEST.json`。
