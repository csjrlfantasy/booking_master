# 黑盒测试 —— 课堂教案

**时长**：45分钟 | **案例**：票多星(TicketMore) | **教具**：Swagger + Postman

---

## 课程目标

> 上完这节课，学生能回答三个问题：
> 1. 黑盒测试到底是什么？（一句话说清楚）
> 2. 拿到一个功能，怎么测？（有套路，不是乱点）
> 3. 黑盒测试能发现哪些类型的Bug？（看得到边界）

## 环节一：一个Bug引发的思考（5min）

### 开场：现场演示一个真实Bug

> 打开票多星Swagger页面，当着学生的面操作。

**操作1**：注册新用户 —— username: `test_001`, password: `123456`, phone: `13800001111`
→ 成功 ✓

**操作2**：注册 —— username: `test_001`, password: `123456`, phone: `13800002222`
→ `code=100106, message="用户名已存在"` ✓（预期内）

**操作3**：注册 —— username: `""`(空), password: `123456`, phone: `13800003333`
→ `code=100601, message="缺少必填参数"` ✓（预期内）

**操作4**：注册 —— username: `"><script>alert(1)</script>`, password: `123456`, phone: `13800004444`
→ ？

> **提问**：操作4会返回什么？

*让学生猜。然后实际执行，展示结果。*

```
如果返回 code=0 → XSS漏洞！用户名存入了HTML标签
如果返回 code=100602 → 做了输入校验，安全
```

> **这，就是黑盒测试。** 你不知道后端代码怎么写的，你只管输入各种数据，看输出对不对。

### 一句话定义

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│   黑盒测试 = 不看代码，只看输入 → 输出是否符合预期        │
│                                                         │
│   你不需要知道里面是"Java写的"还是"Python写的"            │
│   你只需要知道：给什么输入 → 应该得到什么输出             │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 三种测试视角对比

```
  白盒测试                灰盒测试                黑盒测试
  ┌─────────┐           ┌─────────┐           ┌─────────┐
  │  ┌─────┐ │           │  ┌──┐   │           │  ██████  │
  │  │全看光│ │           │  │半透│  │           │  ██████  │
  │  │ 代码 │ │           │  │ 明 │  │           │  ██████  │
  │  └─────┘ │           │  └──┘   │           │  ██████  │
  └─────────┘           └─────────┘           └─────────┘
  开发者视角             混合视角              用户视角
  "这段if分支没覆盖"     "数据库里这条记录       "我点了支付，
                        有没有被改？"            钱扣了吗？"
```

## 环节二：三句话讲透黑盒测试（3min）

### 第一句：你测的是"行为"，不是"代码"

```
用户注册 ──输入──▶  [  系  统  ] ──输出──▶ 注册成功 / 失败原因
                       ▲
                       │
                 你不用关心里面是 if-else 还是 switch-case
                 你只关心：什么输入 → 什么输出
```

### 第二句：用例来自"需求"，不是来自"代码"

| 需求说 | 所以你要测 |
|--------|-----------|
| "密码6-20位" | 输入5位、6位、20位、21位 |
| "手机号必填" | 不填手机号、填格式错误的手机号 |
| "用户名唯一" | 重复的用户名 |
| "支付金额=订单金额" | 金额少0.01、金额多0.01、金额=0 |

> **需求文档就是你的测试地图。** 地图上没有的路，你不需要走。

### 第三句：黑盒不"低级"，黑盒找的是用户会遇到的Bug

```
  白盒能发现的Bug          黑盒能发现的Bug
  ┌────────────────┐      ┌────────────────┐
  │ 空指针异常       │      │ 支付金额少扣0.01 │ ← 用户真的会遇到
  │ 内存泄漏         │      │ 优惠券能用两次   │ ← 用户真的会遇到
  │ 死循环           │      │ 评分可以打6星   │ ← 用户真的会遇到
  │ 数据库连接未释放  │      │ 已取消订单还能付 │ ← 用户真的会遇到
  └────────────────┘      └────────────────┘
```

### 方法1：等价类划分法（6min）

**一句话**：把海量输入分门别类，每类挑一个代表来测。

**为什么需要它？**
```
手机号有 10^11 种可能 → 穷举不可能
等价类划分后       → 只需要测 5-6 个代表值
```

**案例演示：票多星支付渠道选择**

```
需求：payChannel 支持 alipay / wechat / bank / unionpay 四种

  所有可能的字符串（无穷多种）
 ┌────────────────────────────────────────────┐
 │                                            │
 │ ┌────────有效等价类────────┐  ┌──无效等价类──────────────────┐ │
 │ │ alipay  wechat          │  │ ""       (空字符串)             │ │
 │ │ bank    unionpay        │  │ "bitcoin"(不支持的值)           │ │
 │ │                         │  │ null     (不传)                │ │
 │ │ 每类测1个 = 4条用例      │  │ "Alipay" (大小写？看需求)       │ │
 │ └─────────────────────────┘  └──────────────────────────────┘ │
 │                                            │
 └────────────────────────────────────────────┘

结论：4个有效 + 3个无效 = 7条用例，覆盖了无穷多种输入
```

**口诀：**

> **有效等价类可以组合，无效等价类必须独立。**
>
> 一条用例可以同时测"合法用户名+合法密码+合法手机号"，
> 但一条用例只能测一个无效输入，否则你不知道是哪个触发的报错。

**快速练习（1min）：**

> 票多星用户评论评分 `rating`，范围1-5的整数。写出等价类。

```
答案：
  有效：rating=3（代表值）
  无效：rating=0（小于1）、rating=6（大于5）、rating=3.5（非整数）、rating=空
```

### 方法2：边界值分析法（5min）

**一句话**：Bug最爱蹲在边界上，所以你专门测边界。

**为什么边界Bug多？**
- 程序员写 `if (x > 5)` 还是 `if (x >= 5)`，经常搞混
- 数组从0开始还是从1开始，永远有人写错
- 时区、闰年、夏令时……边界是Bug的高发区

**边界值三点法：**

```
          边界值 = N
              │
    ┌─────────┼─────────┐
    │         │         │
    ▼         ▼         ▼
   N-1        N        N+1
 (边界下)   (边界)   (边界上)
  拒绝       接受      拒绝


实战：票多星退款费率边界

  BR-REFUND-001: 演出前 >=7天 → 退100%
  BR-REFUND-002: 演出前 3-7天 → 退70%
  BR-REFUND-003: 演出前 1-3天 → 退50%
  BR-REFUND-004: 演出前 <1天  → 退0%

         168h              72h              24h          演出开始
           │                │                │              │
    ───────┼────────────────┼────────────────┼──────────────┼────▶ 时间
           │    退100%      │    退70%      │    退50%     │ 0%
           │                │                │              │
    测: 168h ✓        测: 72h ✓       测: 24h ✓      测: 24h-1min ✗
    测: 167h59m ✗     测: 71h59m ✗    测: 23h59m ✗

6个边界值 → 6条用例 → 比你写20条随机时间更精准
```

**口诀：**

> **测边界不是测"最大值和最小值"，而是测"刚好满足"和"刚好不满足"的分界线。**

**快速练习（1min）：**

> 票多星订单每人限购10张。写出边界值用例。

```
答案：
  9张 → 应成功（max-1）
  10张 → 应成功（max）
  11张 → 应失败（max+1）
```

### 方法3：判定表法（5min）

**一句话**：当结果由多个条件共同决定时，画张表，一个组合一行。

**什么时候用？** —— 需求文档里出现超过2个"如果……则……"

**案例演示：票多星退款资格判断**

```
条件：
  C1: 订单已支付？（Y/N）
  C2: 已申请过退款？（Y/N）
  C3: 距演出时间？   （>=7天 / 3-7天 / 1-3天 / <1天）

动作：
  退100% / 退70% / 退50% / 拒绝


        判定表（化简后）
┌────┬────┬────┬────┬────┬────┬────┐
│规则│ R1 │ R2 │ R3 │ R4 │ R5 │ R6 │
├────┼────┼────┼────┼────┼────┼────┤
│C1  │ Y  │ Y  │ Y  │ Y  │ N  │ Y  │
│C2  │ N  │ N  │ N  │ N  │ -  │ Y  │
│C3  │≥7天│3-7 │1-3 │<1天│ -  │ -  │
├────┼────┼────┼────┼────┼────┼────┤
│100%│ ✓  │    │    │    │    │    │
│70% │    │ ✓  │    │    │    │    │
│50% │    │    │ ✓  │    │    │    │
│拒-时│    │    │    │ ✓  │    │    │
│拒-付│    │    │    │    │ ✓  │    │
│拒-重│    │    │    │    │    │ ✓  │
└────┴────┴────┴────┴────┴────┴────┘

  3个条件 × 各自的取值 = 4×2×2 = 16种理论组合
  化简后 = 6条规则 = 6条用例
```

**口诀：**

> **条件做乘法，动作做加法。画完表再化简，重复动作合并掉。**

### 方法4：状态转换法（5min）

**一句话**：系统里的东西会"变状态"，你要测每一种合法的变化，也要测每一种非法的变化被拦住。

**案例演示：票多星支付状态机**

```
                    创建支付
                       │
                       ▼
                 ┌──────────┐
                 │ PENDING  │──── 超时/取消 ──▶ CLOSED ✗
                 │  待支付   │
                 └────┬─────┘
                      │ mock-pay成功
                      ▼
                 ┌──────────┐
                 │ SUCCESS  │──── 申请退款 ──▶ REFUNDING ──▶ REFUNDED
                 │  支付成功 │
                 └──────────┘
                      │ mock-pay失败
                      ▼
                 ┌──────────┐
                 │ FAILED   │
                 │  支付失败 │
                 └──────────┘


合法路径（至少4条用例）：
  ✅ PENDING → SUCCESS （正常支付）
  ✅ PENDING → FAILED  （支付失败）
  ✅ PENDING → CLOSED  （超时关闭）
  ✅ SUCCESS → REFUNDING → REFUNDED （退款）

非法路径（至少3条用例）：
  ❌ SUCCESS → PENDING  （已支付的退回到待支付？不行！）
  ❌ CLOSED → SUCCESS   （已关闭的还能支付？不行！）
  ❌ FAILED → 直接SUCCESS（失败的跳过支付变成功？不行！）
```

**口诀：**

> **合法路径全走一遍，非法路径全拦一遍。**

**快速练习（1min）：**

> 票多星优惠券状态：未使用(0)→已使用(1)/已过期(2)/已禁用(3)。已使用的券能变回未使用吗？

```
答案：不能。已使用→未使用是非法路径，应被拦截。
     同理：已过期→未使用、已禁用→未使用，都应该是非法的。
```

### 方法5：场景法（4min）

**一句话**：模拟真实用户的操作流程，从打开App到完成目标。

**案例演示：票多星购票支付全流程**

```
用户旅程图：

  [浏览票品] → [查看详情] → [选场次票档] → [加入购物车]
                                              │
                                              ▼
  [查看订单] ← [支付成功] ← [确认支付] ← [创建订单]
      │                          │
      │                          ├── [使用优惠券]（备选）
      │                          └── [支付失败]（异常）
      │
      └── [申请退款]（备选）


  Happy Path（基本流）：
    浏览→详情→加购→下单→支付→成功 = 1条端到端用例

  Alternative Path（备选流）：
    不使用购物车直接购买 = 1条用例
    使用优惠券后支付 = 1条用例

  Error Path（异常流）：
    支付过程中余额不足 = 1条用例
    支付超时订单被取消 = 1条用例

  共5条，覆盖用户最可能走的所有路径
```

**口诀：**

> **先走通主流程，再分叉到备选和异常。主流程不通，其他都白费。**

### 五法速查表

| 你遇到的情况 | 用这个方法 | 关键词 |
|-------------|-----------|--------|
| 输入有范围/格式限制 | **等价类划分** | "分类取代表" |
| 输入有明确边界 | **边界值分析** | "min-1, min, max, max+1" |
| 多个条件决定一个结果 | **判定表法** | "如果…则…否则如果…" |
| 对象有状态变化 | **状态转换法** | "从X变成Y" |
| 描述的是用户操作流程 | **场景法** | "用户先…然后…最后…" |

## 环节四：实战——你来找Bug（8min）

### 题目

> 票多星有一个功能：**用户修改密码**。
>
> 接口：`PUT /api/user/password`
> 需求：
> - oldPassword：必填，必须与当前密码一致
> - newPassword：必填，6-20位
> - confirmPassword：必填，必须与newPassword一致
>
> 给你3分钟，用今天学的方法设计尽可能多的用例。每条用例写清楚：
> **输入什么 → 预期输出什么**

*（3分钟后收答案，投影展示参考答案）*

### 参考答案

```
等价类划分：
  1. 全部正确输入 → code=0 修改成功
  2. oldPassword为空 → code=100601
  3. newPassword为空 → code=100601
  4. oldPassword错误 → code=100103

边界值分析：
  5. newPassword=5位 → code=100602 (min-1)
  6. newPassword=6位 → code=0 (min)
  7. newPassword=20位 → code=0 (max)
  8. newPassword=21位 → code=100602 (max+1)

判定表/组合：
  9. confirmPassword ≠ newPassword → code=100602
  10. oldPassword错误+newPassword太短 → 只报第一个错误

场景法：
  11. 登录→改密码→用旧密码登录失败→用新密码登录成功 ✓

共11条用例，5分钟设计的，覆盖了大部分Bug。
```

### 三个核心认知

| 认知 | 说明 |
|------|------|
| 黑盒 ≠ 低端 | 黑盒测的是用户真正会遇到的问题，不是代码的内部缺陷 |
| 用例 ≠ 瞎写 | 5种方法是你手里的工具，不同场景用不同方法，组合使用 |
| 测试 ≠ 验证 | 测试的目的是**发现缺陷**，不是为了证明系统没问题 |

## 讲师备忘

1. **环节一的现场演示是关键**：务必提前启动票多星后端服务，确保Swagger可用
2. **控制时间**：5种方法25分钟，平均每种5分钟，不要在一种方法上超时
3. **XSS那个例子**如果后端做了校验不会返回code=0，那就换一个例子——比如输入超长字符串看有没有长度限制
4. **实战环节**让学生写在纸上或打字，然后挑2-3个人分享，最后投影参考答案
5. 如果时间充裕，可以打开自动化测试脚本 `test_payment.py` 让学生看到黑盒测试如何变成自动化
