# 测试计划课程教案 —— 30分钟课堂教学设计

**课程主题**：什么是测试计划 & 如何制定测试计划
**授课对象**：QA工程师 / 测试新人
**课程时长**：30分钟
**教学案例**：票多星(TicketMore)票务平台
**教学方法**：理论讲解 + 案例演示 + 互动提问

---

| 维度 | 目标 |
|------|------|
| 知识 | 理解测试计划的定义、目的和核心组成要素 |
| 技能 | 掌握测试计划的编写方法，能独立完成中小模块的测试计划 |
| 思维 | 建立"先计划再执行"的测试工程思维，理解风险驱动的测试策略 |

## 三、详细教学脚本

### 【环节一】导入：为什么需要测试计划（4分钟）

**（0:00 - 0:01）开场提问**

> 各位同学，假设你明天要测试一个新上线的支付功能。产品经理给了你一份需求文档，开发说"代码已经写好了，你测吧"。你会怎么做？

*（等待学生回答 30 秒）*

常见的回答是："打开系统，点来点去，看看能不能付款。"

**（0:01 - 0:02）真实案例引入**

> 2023年某电商平台双11当天，支付模块在峰值流量下出现大面积超时，导致用户重复下单被多次扣款。事后复盘发现：测试阶段根本没做过并发支付测试，也没有支付超时的异常场景覆盖。如果有一份完整的测试计划，这个事故大概率可以避免。

> **测试计划不是写文档应付流程，而是你在动手测试之前的作战地图。**

**（0:02 - 0:03）引出定义**

> **测试计划（Test Plan）** 是一份正式文档，描述测试范围、测试策略、资源分配、进度安排和风险评估。它回答一个问题：**谁在什么时候用什么方法测什么，测到什么程度算完？**

来看 IEEE 829 标准对测试计划的定义：

```
测试计划 = 测试范围 + 测试策略 + 资源 + 进度 + 风险 + 准入/准出标准
```

**（0:03 - 0:04）结合票多星项目介绍背景**

> 今天我们用这个真实项目"票多星"来展开。票多星是一个演出票务平台，用户可以浏览演出、选座购票、加入购物车、使用优惠券、发起支付。后端是 Spring Boot + MyBatis Plus，有 60+ 个 API 接口，分为用户、票务、订单、购物车、优惠券、支付、后台管理 7 个模块。

> 我们今天聚焦其中的**支付模块**，来演示如何制定一份测试计划。

#### 要素2：测试范围 —— 测什么、不测什么（2 min）

**（0:05 - 0:07）**

> 测试范围是最容易被忽略但又最重要的部分。**说不测什么，比说测什么更需要勇气。**

**为什么要明确"不测"？**
- 无限测试是不可能的，时间永远是有限的
- 避免后期扯皮："这个bug怎么没测出来？" —— "因为测试计划里明确写了这部分不在此次范围。"

**PPT展示 —— 票多星支付模块测试范围：**

```
【范围内 In-Scope】
✓ 支付方式选择（余额支付、支付宝、微信支付、银行卡）
✓ 支付接口调用与返回处理
✓ 支付成功后的订单状态更新（PENDING_PAYMENT → PAID）
✓ 支付失败场景（余额不足、网络超时、支付取消）
✓ 支付超时自动取消（15分钟未支付订单自动取消）
✓ 退款申请与退款状态查询
✓ 支付回调签名验证
✓ 并发支付（同一订单不能重复支付）
✓ 支付信息加密传输（HTTPS + 敏感字段脱敏）

【范围外 Out-of-Scope】
✗ 真实第三方支付渠道对接（本期使用Mock）
✗ 对账文件下载与解析（属于财务系统）
✗ 支付手续费计算（暂未实现）
✗ 跨境支付与汇率换算
✗ 移动端原生支付SDK集成（本期仅测API层）
```

> **记住一个原则**：范围跟着需求走。需求文档里有的功能，必须在范围内。需求文档里没有的，跟产品确认后再决定。

#### 要素3：测试策略 —— 怎么测（2 min）

**（0:07 - 0:09）**

> 测试策略回答一个核心问题：**用什么方法，在什么层级，测到什么深度？**

**PPT展示 —— 票多星支付模块测试策略：**

```
【测试分层策略 —— 测试金字塔】

        /\
       /  \         E2E：关键支付流程（创建订单→发起支付→支付成功→订单状态更新）
      /    \        [3-5条核心场景，手动+自动化]
     /------\
    / 集成测试 \     集成测试：API接口级测试（支付创建、Mock支付、状态查询、退款）
   /          \    [12-15条，Python + Pytest 自动化]
  /------------\
 /   单元测试     \  单元测试：Service层业务逻辑（金额计算、签名验证、状态机转换）
/                \ [20+条，JUnit 5，覆盖关键分支]
```

**针对支付模块的具体策略：**

| 测试类型 | 方法 | 工具 | 说明 |
|----------|------|------|------|
| 功能测试 | 黑盒 + 场景法 | Postman / Swagger | 覆盖所有支付方式、支付状态转换 |
| 接口测试 | 自动化脚本 | Python + Pytest + Allure | 回归测试每天跑一次 |
| 安全测试 | 渗透测试 + 代码审查 | Burp Suite / 人工 | 签名验证、金额篡改、重放攻击 |
| 性能测试 | 压力测试 | JMeter | 并发100用户发起支付 |
| 兼容性测试 | 手动 | Chrome/Firefox/Edge/Safari | 前端支付页面（如有） |
| 异常测试 | 手工 + 自动化 | Mock服务 | 网络超时、服务宕机、第三方返回异常 |

> **策略选择的底层逻辑**：高频变更的 → 自动化；一次性验证的 → 手动；涉及金钱的 → 加倍测试深度。

#### 要素4：测试用例设计思路（1.5 min）

**（0:09 - 0:10:30）**

> 我们不在这里写完整的用例，但测试计划中要说清楚**用例设计的方法和覆盖维度**。

**PPT展示 —— 用例设计维度：**

```
【支付模块用例设计维度】

1. 正常场景（Happy Path）
   - 选择支付方式 → 发起支付 → 支付成功 → 订单状态更新为PAID
   - 每种支付方式至少1条

2. 异常场景（Error Path）
   - 支付金额与实际订单金额不匹配
   - 余额不足 / 支付超时
   - 对已支付的订单再次发起支付（幂等性）
   - 对已取消的订单发起支付
   - 支付回调签名验证失败

3. 边界场景（Boundary）
   - 支付金额 = 订单金额（边界：零元订单）
   - 支付超时临界点（14分59秒 vs 15分01秒）
   - 退款百分比边界（7天/3天/1天的退票费率分界）

4. 状态机场景
   - 合法的状态转换：PENDING_PAYMENT → PAID → TICKET_ISSUED
   - 非法的状态转换：CANCELLED → PAID（应拒绝）
```

> **设计原则一句话**：先覆盖 Happy Path 保证功能可用，再覆盖 Error Path 保证系统不崩，最后用边界和状态机保证逻辑严密。

【前置条件】

#### 要素6：风险评估与应对（1.5 min）

**（0:11:30 - 0:13:00）**

> 这是测试计划中最体现测试工程师价值的部分。**别人看功能，你看风险。**

**PPT展示 —— 支付模块风险评估矩阵：**

```
【风险矩阵】  影响程度：高/中/低  ×  发生概率：高/中/低

┌────────────────────┬────────┬────────┬──────────────────────────┐
│       风险项        │  影响  │  概率  │        应对措施           │
├────────────────────┼────────┼────────┼──────────────────────────┤
│ 支付接口超时导致    │   高   │   中   │ 设置3秒超时+重试机制      │
│ 用户重复扣款        │        │        │ 测试用例覆盖幂等性验证    │
├────────────────────┼────────┼────────┼──────────────────────────┤
│ 回调签名被绕过      │   高   │   低   │ 代码审查签名逻辑          │
│ 导致伪造支付成功    │        │        │ 渗透测试验证              │
├────────────────────┼────────┼────────┼──────────────────────────┤
│ 并发场景下订单      │   高   │   中   │ 并发测试(100线程)         │
│ 被重复支付          │        │        │ 数据库乐观锁验证          │
├────────────────────┼────────┼────────┼──────────────────────────┤
│ Mock与真实支付      │   中   │   高   │ Mock尽量模拟真实返回结构  │
│ 接口行为不一致      │        │        │ 上线前做1次真实沙箱验证    │
├────────────────────┼────────┼────────┼──────────────────────────┤
│ 支付超时与订单      │   中   │   中   │ 明确15分钟定时任务        │
│ 取消的时序冲突      │        │        │ 测试临界时间点的并发场景   │
└────────────────────┴────────┴────────┴──────────────────────────┘
```

> **风险识别技巧**：第一看钱（支付、退款），第二看并发（抢票、秒杀），第三看外部依赖（第三方接口不可控），第四看数据一致性（状态机转换）。

Day 7 (6/5)   ████ 测试报告编写 + 上线建议

【准出标准 —— 满足以下所有条件方可上线】

☑ 安全扫描无高危漏洞
☑ 并发场景错误率 < 0.5%
☑ 回归测试全部通过
☑ 测试报告已通过评审
```

> **准出标准是测试计划里最硬的东西**——它是你将来跟项目经理说"不能上线"的底气。

#### 要素8：测试报告与总结（0.5 min）

**（0:14:00 - 0:14:30）**

> 测试计划里要预先定义好测试报告的模板和内容。不要等测完了再想怎么写报告。

**测试报告应包含：**
- 测试执行情况（计划 vs 实际，用例通过率）
- 缺陷分布（按模块/严重程度/类型的统计图）
- 性能数据（并发下的响应时间分布）
- 遗留风险（已知未修复的缺陷及规避方案）
- **上线建议** —— 这是测试报告最重要的输出：Go / No-Go

### 【环节三】案例实操：支付模块测试计划制定（10分钟）

---

**（0:14:30 - 0:18:30）第一步：分析需求，提取测试点（4 min）**

> 现在我们来实操。第一个问题是：**给你票多星支付模块的需求，你怎么提取测试点？**

**现场演示 —— 从API接口反推测试需求：**

票多星支付模块有7个API端点（展示 Swagger 截图）：

```
POST /api/payment/create          — 创建支付
POST /api/payment/mock-pay        — 模拟支付
GET  /api/payment/status/{orderNo} — 查询支付状态
POST /api/payment/refund           — 申请退款
GET  /api/payment/refund/{orderNo} — 退款状态查询
DELETE /api/payment/{orderNo}      — 取消支付
POST /api/payment/callback         — 支付网关回调
```

**从7个接口推导出测试点：**

| 接口 | 测试维度 | 测试点数量 |
|------|----------|-----------|
| /payment/create | 正常创建、重复创建、无效订单号、已取消订单、金额不匹配 | 6 |
| /payment/mock-pay | 成功支付、余额不足、已支付订单再次支付 | 4 |
| /payment/status | 存在/不存在的订单号、非本人订单 | 3 |
| /payment/refund | 正常退款、重复退款、不符合退款条件的订单 | 4 |
| /payment/refund/{orderNo} | 退款中/已退款/退款失败状态查询 | 3 |
| /payment/{orderNo} | 取消待支付订单、取消已支付订单（应拒绝） | 3 |
| /payment/callback | 正确签名、错误签名、重放回调、篡改金额 | 5 |
| **合计** | | **约28个测试点** |

> **这就是从接口出发做测试分析的思路：接口 → 参数组合 → 正常/异常/边界 → 测试点**。

---

**（0:18:30 - 0:21:30）第二步：设计测试策略（3 min）**

> 28个测试点，不可能全部手工测一遍。怎么分配？

**PPT展示 —— 测试分配策略：**

```
【测试点分配】

自动化测试（18个，64%）
├── Python + Pytest 接口自动化（核心回归用例）
│   ├── test_payment_create.py    — 创建支付 4条
│   ├── test_payment_mock_pay.py  — 模拟支付 4条
│   ├── test_payment_status.py    — 状态查询 2条
│   ├── test_payment_refund.py    — 退款流程 4条
│   └── test_payment_callback.py  — 回调安全 4条
│
└── JUnit 单元测试（Service层）
    ├── PaymentService 金额计算、签名生成
    └── OrderService 状态机转换逻辑

手动测试（10个，36%）
├── 首次探索性测试（新功能的第一次验证）
├── 安全测试（签名伪造、金额篡改、重放攻击）
├── 并发场景（JMeter 100线程并发支付同一订单）
└── UI兼容性（支付页面在不同浏览器上的表现）
```

> **分配原则**：回归频率高的 → 自动化；需要人工判断的（安全、体验、探索性） → 手动。

---

**（0:21:30 - 0:24:30）第三步：编写2条关键测试用例（3 min）**

> 测试计划中不需要写全部用例，但关键场景的用例要写出来，让大家理解测试深度。

**现场编写示例 —— TC-PAY-001（支付成功主流程）：**

```
┌─────────────────────────────────────────────────────────┐
│ 用例编号: TC-PAY-001                                     │

### 【环节四】总结与常见误区（4分钟）

---

**（0:24:30 - 0:27:00）核心要点回顾（2.5 min）**

> 最后我们回顾一下今天的内容。

**测试计划的本质：**

```
          ┌──────────────┐
          │   为什么要测？  │ ← 测试目标
          ├──────────────┤
          │   测什么？     │ ← 测试范围
          ├──────────────┤
          │   怎么测？     │ ← 测试策略
          ├──────────────┤
          │   谁来测？     │ ← 人员分工
          ├──────────────┤
          │   什么时候测？  │ ← 进度安排
          ├──────────────┤
          │   在哪测？     │ ← 测试环境
          ├──────────────┤
          │   有什么风险？  │ ← 风险评估
          ├──────────────┤
          │   测完了吗？   │ ← 准出标准
          └──────────────┘
```

> 记住一句话：**测试计划不是写给领导看的文档，而是写给自己和团队用的作战地图。你写得越清楚，测得就越稳。**

**（0:27:00 - 0:28:30）常见误区（1.5 min）**

| 误区 | 正确做法 |
|------|----------|
| "测试计划就是抄模板" | 模板是骨架，内容要结合具体项目填充 |
| "把测试用例全部写进计划里" | 计划是概要，用例单独管理。计划里只放核心用例作为样例 |
| "风险分析随便写几条" | 风险要结合业务特点。支付模块的钱、票务模块的库存、用户模块的隐私，各有侧重 |
| "进度排满不预留buffer" | 缺陷修复、需求变更、环境问题都会吃掉时间。预留20-30%的缓冲 |
| "测试报告测完再说" | 计划阶段就定义好报告模板和准出标准，否则最后没法判断"测完了没有" |
| "一次性写完再也不改" | 测试计划是**活文档**，需求变了、发现了新风险，都要更新计划 |
